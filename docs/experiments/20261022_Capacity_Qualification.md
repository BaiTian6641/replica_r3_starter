## Exact content and provenance

The offline [workload builder](../../scripts/make_capacity_fixtures.py) reads the existing sealed MiniCPM5 tokenizer/template, without loading model weights or changing source files. Both workloads contain eight train and eight development episodes. Every split contains each answer `0..7` exactly once, and every claimed full length includes the complete native chat prompt, one answer token and supervised EOS.

| Workload | Full sequence tokens, all 16 rows | Native prompt tokens | Supervised tokens | Support tokens | Observed records per row | Auxiliary register writes |
|---|---:|---:|---:|---:|---:|---:|
| [256 manifest](../../data/diagnostics/capacity_256/manifest.json) | 256 | 254 | 2 | 197 | 19 | 15 |
| [512 manifest](../../data/diagnostics/capacity_512/manifest.json) | 512 | 510 | 2 | 453 | 45 | 41 |

The source stories contain an unsigned register world, two historical/current `MASK` writes, and chronological writes to auxiliary registers `R0..R3`. The query asks for input XOR the latest observed mask. Width-4/mask-1 train source families and width-5/mask-2 development source families have separate world IDs, source IDs and split groups. Labels are generated by native integer XOR and independently checked using per-bit arithmetic over parsed observations. Wrong labels, missing or reordered facts, changed provenance and injected answer annotations fail validation.

Exact length comes from complete register events and a truthful status record: `Status: clock=16.` at 256 and `Ready.` at 512. There is no whitespace/token padding or evidence/answer truncation. The manifests retain per-row source, support, prompt, task and target counts; actual-length and supervised-token histograms; every selected audit record; data hashes; source revision/lock and tokenizer-file hashes; template hash; and generator hash.

These are synthetic **capacity fixtures**, not quality-training data. The auxiliary histories deliberately create real attended content while leaving a simple solver-grounded target. Finite-width registers produce repeated values and overwrites at distinct clocks. Deterministic world IDs and shared generators do not create independent natural-world observations, and the two simple transform families do not establish broad transfer. Their purpose is to expose the full model to the actual declared sequence/activation load with intact, causal evidence. D0 includes the records in its native text prompt; a later D2 run would additionally exercise its support writer and remains a separate qualification.

The executed build commands were:

The builder refuses existing output directories. A new reproduction can use `--output-root` with a fresh location. Twelve capacity-fixture tests passed, including real pinned-tokenizer lengths; a deterministic rebuild matched every saved row and per-row audit exactly. ## Bounded training and stop criteria

For each length, begin from the same fresh sealed original model, retain all 2,516,756,480 original parameters trainable, and use FP32 MPS with nonreentrant activation checkpointing. The optimizer remains the project experiment with int8 hidden-matrix Muon momentum and auxiliary FP32 AdamW. Use microbatch one, answer-balanced accumulation eight, matched base rates `1e-4`, two-update warmup, constant schedule, zero weight decay and seed 17.

Each length completed two total updates in two fresh processes: update 1, completed-update checkpoint, then restore and update 2. The first rate was `5e-5`; the second was `1e-4`. A complete model/runtime checkpoint was saved at each update, and all four exported-model reload comparisons passed. Generation was disabled for this capacity screen; development evaluation was teacher-forced loss. Each effective update processed 2,048 sequence tokens at length 256 or 4,096 at length 512, with 16 supervised tokens in either case.

The external watchdog uses these declared sampled thresholds:

| Signal | Stop condition |
|---|---|
| MPS driver allocation | Any observed value at or above 40 GiB |
| Host swap occupancy growth from process baseline | At least 512 MiB for three consecutive host samples |
| Host memory-free percentage from `memory_pressure -Q` | At or below 15% for three consecutive host samples; refuse an already-low baseline |
| Missing/stale driver telemetry | More than 30 seconds without a valid observed driver sample |

MPS profile polling is nominally 0.25 seconds and host polling two seconds. The guard first interrupts the child to preserve available failure/profile evidence, then escalates if it remains unresponsive. Existing OS and allocator safeguards remain in place. These are sampled operational stops, not an OOM guarantee. Host measurements describe the whole machine, MPS/RSS counters overlap, and unchanged swap endpoints do not prove absence of swap traffic.

Do not start 512 until 256 passes the scoped review. Any seal, scope, numerical, artifact, resume or guard failure stops progression and retains the negative evidence. A watchdog status of `completed_within_declared_sampled_limits` alone does not establish the complete capacity gate; trainer reports, phase samples, checkpoint receipts and audits must agree.
