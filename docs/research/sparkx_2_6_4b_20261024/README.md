The recommended target is a single trainable Spark-based model containing a visual encoder, spatial and temporal adapters, a recurrent workspace, neural memory, and a learned improvement policy. Its forward computation must actually use those components. Exact evidence storage, optimizer execution and independent evaluation remain runtime services. This makes the abilities intrinsic to model computation while preserving reproducibility and a way to detect failed updates.

The first achievable milestone is an image-dependent, stateful model that learns a small new visual concept from a verified demonstration, recalls it after the original observation leaves context, and improves on new examples without damaging existing skills. A general, indefinitely improving cognitive system is a research objective, not an established consequence of attaching memory modules.

**Main decisions.** Preserve Spark's pretrained attention and MLP blocks initially. Introduce independently gated residual readers and a separately trained visual bridge. Establish a reliable linear-memory control before testing nonlinear adaptive memory. Add explicit spatial locations, region identities and timestamps before training visual reasoning. Upgrade the core to attend to those structured visual features, supervise useful inspection and memory actions, then train bounded improvement from verified outcomes. Study genuine multi-timescale self-modification only after simpler adaptation works.

The repository is a useful engineering foundation, but its current learned-memory candidate is rejected: initial facts **0/64**, corrections **0/16**, unaffected facts **0/48**. Its **56/192** total matches disabled memory. The exact selective-context control reaches **184/192**, but also fails its complete reference gate. These results diagnose a learning/readout problem; they do not justify abandoning source integrity or claiming that Spark alone fixes it. See the [canonical verdict](../../../reports/memory_reliability_v5_scorer_fix_eval02/verdict_final.json).

Spark's official pinned configuration and weight index describe **4,112,079,360** unique parameters, 36 decoder layers and width 2,560. The language weights alone require approximately **7.66 GiB in BF16** or **15.32 GiB in FP32**. Full FP32 Adam training requires approximately **61.27 GiB for parameters, gradients and moments alone**. On the repository's 64 GiB Mac with a 50 GiB driver guard, begin with frozen-backbone/module training and measured adapter tuning. The 24 GB CUDA target also needs its own capacity qualification. [Official source and index](https://huggingface.co/XHToken/Spark-X2.6-4B/tree/66e3ae7bee54e0a523d692cb8ef841f35409807b).

The proposed next-phase schedule keeps MiniCPM5 as the working regression baseline while developing Spark's adapter and isolated perception path. A completed negative memory diagnosis does not have to delay text parity or image alignment after the required integrity/interface repairs. It does prevent promotion of an integrated system whose claims depend on that failed memory mechanism. This proposal elaborates the requested Spark target; it does not launch or silently replace the existing MiniCPM execution campaign.

The latest repository update adds three still-open prerequisites: caller-bound exact-context verification, complete ordered training-route auditing, and representation-preserving memory rebuild. Its [official FP8/BF16 plan](../../architecture/20_Spark_X2_6_FP8_Preparation_Plan.md) prepares FP8 as an adaptation-base candidate with BF16 as the independent control. This report incorporates that path without claiming FP8 backward/optimizer support on the M2 Ultra.
